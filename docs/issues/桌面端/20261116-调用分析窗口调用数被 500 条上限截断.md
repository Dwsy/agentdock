# Issue: 调用分析窗口调用数被 500 条上限截断

## Goal

调用分析页的「窗口调用」如实反映最近 5 分钟的调用次数，不再被固定条数上限截断。

## 背景/问题

`observability.Recorder` 用固定容量 500 的环形缓冲保存最近调用，`Snapshot.WindowCalls` 直接取环的长度，桌面端却把这张卡标成「最近 5 分钟」。调用频率一高，窗口调用数就恒为 500，与「总调用」严重脱节；同一份环还被用来算 `tool_stats`，所以工具调用分布永远只统计最近 500 次（用户截图里 9 个工具的次数相加正好 500）。

## 验收标准 (Acceptance Criteria)

- [x] WHEN 统计窗口内的调用超过 500 次，窗口调用数 SHALL 等于实际次数
- [x] WHEN 聚合工具调用分布，SHALL 覆盖整个统计窗口而不是最近 500 条
- [x] WHERE 最近调用流水（Activity 页的 `recent_calls`），SHALL 仍受环形缓冲容量约束
- [x] IF 窗口内没有调用，窗口调用数 SHALL 为 0
- [x] WHERE 桌面端展示，窗口长度 SHALL 与后端常量一致（5 分钟）
- [x] WHERE 错误率告警，SHALL 与 analytics 窗口同口径（最近 5 分钟内完成的调用）

## 实施阶段

### Phase 1: 规划和准备
- [x] 确认 500 来自 recorder 环形缓冲容量（`DefaultRecentCapacity`），不是 UI 截断
- [x] 确认 `tool_stats` 与 `window_calls` 同源，一起改口径

### Phase 2: 执行
- [x] recorder 增加 5 分钟滚动窗口（`WindowMinutes`），窗口内保留精简统计投影
- [x] `window_calls` / `tool_stats` 改为窗口口径，最近调用环保持 500 条不变
- [x] 错误率告警改用同一个窗口（`Recorder.WindowErrorStats`）

### Phase 3: 验证
- [x] `go test ./internal/observability/ ./internal/app/ ./internal/httpx/`
- [x] `go test -race ./internal/observability/`

### Phase 4: 交付
- [x] 更新文档（PR 记录）

## 关键决策

| 决策 | 理由 |
|------|------|
| 窗口按时间滚动而不是按条数 | 桌面端文案一直是「最近 5 分钟」，条数口径天生会漂移；改成时间口径后文案与实现一致 |
| 窗口只存精简投影（工具/耗时/成败/行数/token），上限 20000 条 | 聚合只需要这些字段；不保留 Stages 等明细，避免高频调用把内存吃光 |
| 最近调用环保持 500 条 | 它服务的是「最近调用流水」，需要跨长时间保留历史，语义与窗口不同 |
| 告警规则与 analytics 窗口同口径 | 告警文案本来就叫「窗口错误率」，用同一个窗口才不会两边数字打架；失败调用要等出窗口才消失，后续成功调用不再清掉告警 |
